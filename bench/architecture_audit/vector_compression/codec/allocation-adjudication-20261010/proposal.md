Original P2 sources, corpus expectations and execution evidence remain unchanged. It authorizes no production implementation or default change; P2–P5 remain HELD until independent review and the remaining actual-owner proofs.

The root's original raw lane passed all 10 admission and 78 serializer commands. Its original calibration exited 2 for the sole `long-root-key-late-escape` case: parser incremental peak 197,041 <= proposed E_JSON 597,552; pair-construction incremental peak 196,987 > proposed E_PLAN 134,604. Final pair-stage retained allocation is 66,676. These are measured requested allocation quantities from the frozen global allocator, including requested old-plus-new capacity before realloc. They are neither RSS nor an allocator-overhead bound. The large separately retained expected-output oracle, fixture BIN and source reader owners appear in the recorded baseline; they must not silently become production-owner policy terms.

The long key is a literal 65,536-byte `z` prefix followed by `\u0061`, decoded to 65,537 bytes. Pinned serde_json's `SliceRead::parse_str_bytes` first extends scratch with the prefix, then appends decoded `a`. Pinned std `RawVec::grow_amortized` chooses max(2*old_capacity, required_capacity), so scratch grows 65,536 -> 131,072. The meter requests old+new before realloc. serde_json's MapKey then invokes StringVisitor, whose `visit_str` calls `to_owned`; pinned str/slice code allocates a distinct key buffer of exactly decoded length. Scratch capacity survives `clear()` and subsequent keys until `serde_json::from_str` returns and drops that object decoder. Borrowed RawValue value subtrees do not become owned Value trees.

The maximum occurs later than that growth: the final `pad` key adds three owned bytes while scratch remains live. The exact construction witness is 131,072 scratch +65,595 bytes of all seven root keys +8*40 root pair slots =196,987. Earlier scratch realloc is 65,536+131,072+55 bytes of prior root keys+8*40 slots =196,983. Copying the long key gives 131,072+65,537+55+8*40 =196,984. These disjoint source-derived sums match the actual recorded maximum; `source-ledger.json` freezes the literal key sizes and predicates.

After all pairs have been built and object decoders have dropped, the exact retained witness is 65,660 key capacities +40*(8 root+4 buffer+8 view pair slots) +24*1 view descriptor +16*(4 buffer refs+4 view refs+4 declaration refs+0 required refs) =66,676. Actual reported OwnedPair=40, RawRef=16, Pairs=24, Edit=56 and Root=72 are pinned to the root's compiler/artifact closure. Edit and Root are stack values, not separately allocated owners. The three RawRef vectors grow from empty by push; the pinned element-size-dependent Vec minimum capacity is four. `views` uses a TrustedLen map/collect with one exact descriptor. This accounting does not infer sizes for future Plan/Edit/receipt/path structures that do not exist yet.

Retain the current exact raw-value serializer strategy. Rework only its phase accounting: charge construction payload as 3J, and charge retained key payload as J after every contributing decoder/scratch owner is dropped. The additional J is not permanent scratch. For this one witness, provisional terms become E_BUILD=3J+128K+256(V+A)=200,434 and E_RETAIN=J+128K+256(V+A)=68,774 (J=65,830, K=21, V=1, A=0). They cover this measured witness with margins 3,447 and 2,098; that is a witness comparison, not future-production proof of 128K or 256(V+A).

The 3J payload argument depends on a concrete schedule. Every consumed source object is parsed once; distinct root/buffer/view key occurrences contribute their decoded lengths at most once. String cloning requests exact decoded byte length. Only one object decoder scratch owner is live at a time; it is dropped before parsing the next object. During a scratch growth, the previous owned key bytes and the current key's source bytes are disjoint; doubling gives old+new <=3 times the currently required scratch length (plus the minimum-capacity small-case allowance). Thus retained previous key bytes plus scratch growth fit 3J. After growth, retained keys <=J and scratch capacity <=2J; after decoder drop only <=J key payload remains. RawValue's iterative nested grammar uses that same decoder scratch, not a second simultaneously live decoder. Its required nesting bytes correspond to distinct structural source bytes; minimum-capacity and slot growth require separate nonpayload accounting. Repeated graph references must reuse the one physical-view plan rather than reparsing its keys. Any future representation that duplicates the same source object, holds several decoders, rounds key capacity differently, parses arbitrary numeric values, or retains extra owned schema/string data invalidates this schedule and must be re-accounted.

Count actual pair slots and transient slot realloc separately: on the measured target OwnedPair is 40 bytes; large growth old+new <3*m slots yields <120*m bytes, while an initial nonempty Vec needs its four-slot minimum. For one-key objects that minimum is 160 bytes, so `120*pair_nodes` alone is not a valid universal bound. Root/buffer/view consumed property nodes are distinct within admitted K; RawRef arrays and Vec<Pairs> backing are separately identified owners. Their old+new capacities and empty/minimum cases must enter the actual plan ledger. The same bytes cannot also be counted as 256(V+A) descriptors. Keep the 128K and 256(V+A) coefficients HELD until actual owned types, capacity choices and source-count relationships justify them; do not use a passing scaffold to approve them.

Unsupported inputs consume bounded parsing/classification work before returning Unsupported; they cannot be assigned zero memory. Decode arbitrary declared extension names during the construction phase and reject unsupported names before serialization. The scaffold's Decl serializer decodes each name into a temporary String on each count/emission pass. After the real profile admits only its finite known extension names, this temporary name/scratch charge belongs explicitly to the count/emission fixed allowance; the measured witness reports 21 extra requested bytes in each pass. Unknown or arbitrarily long extension names must never reach that reduced phase assumption. Preserve opaque schema/extras RawValue subtrees without interpreting arbitrary application keys as extension declarations. Exact future error strings/receipt owners and refused-source scratch still require their actual live-phase accounting.

Proposed whole-operation schedule, with the existing 128MiB default threshold unchanged:

```
P_read   = I + 65536
P_json   = I + E_JSON
P_build  = I + E_BUILD + 65536
P_decode = I + E_RETAIN + D_stage + 65536
P_emit   = I + E_RETAIN + U + T_upper + 65536
P_identity = 2*I + 65536  # scratch/plan/decoder dropped before independent owned copy
E_peak = max(P_read,P_json,P_build,P_decode,P_emit,P_identity)
         +1024 +actual caller path storage +live producer bridge bytes
```

Any bridge/path/error/receipt owner that survives only selected phases must be assigned to those exact phases before replacing this conservative additive convention. U is settled allocated BIN capacity including bound tail, not merely encoded length. T_upper is the owned final GLB capacity including the selected chunk framing; the ownership transfer of U does not create a second allocation unless a copy actually occurs. A different implementation order requires a new schedule. For the synthetic witness with zero bridge/path storage and no native decoding, E_JSON still dominates: proposed whole E_peak is 664,406 both before and after the construction correction. Therefore the measured term defect does not demonstrate violation of the proposed 128MiB whole-operation threshold or a default gap.

A borrowed-key `Cow<str>` visitor has a real narrow benefit: unescaped keys can borrow source bytes, avoiding their String payload allocations. String and Cow headers are both 24 bytes on the measured target, so OwnedPair remains 40 bytes. Escaped keys still require decoded scratch and a retained owned copy; therefore Cow cannot remove the measured long-key peak. An explicit visitor could use `try_reserve_exact` for owned escaped keys and bounded/fallible pair slot reservation. That is a representation candidate for future ownership review, not an approved prototype; the private C1 numeric helper is not a public codec utility and no new lexer is proposed. Do not claim complete graceful allocation failure because pinned serde scratch growth remains infallible.
